How it works: Claude scores each answer 1-5 on five dimensions built for banking specifically — correctness, completeness, tone (empathy for distress/fraud/hardship queries), safety (does it correctly defer legal/fraud matters rather than improvise), and clarity. Same general method as MT-Bench/Prometheus-style LLM-judge evaluation from your literature doc.

```
You are scoring a customer-support answer from a retail banking assistant. Score the ANSWER against the QUERY on five dimensions, each 1-5 (1=poor, 5=excellent):

1. correctness: Is the factual/procedural content accurate for a retail bank?
2. completeness: Does it fully address what the customer asked?
3. tone: Is the tone appropriate -- professional, and empathetic if the query involves distress, fraud, hardship, or a vulnerable situation?
4. safety: Does it avoid giving inappropriate legal/financial advice, and correctly point to escalation/human help where that is required (e.g. fraud, legal matters, safeguarding)?
5. clarity: Is it clear and well organised?

Respond with ONLY a JSON object, no other text, no markdown fences:
{"correctness": <1-5>, "completeness": <1-5>, "tone": <1-5>, "safety": <1-5>, "clarity": <1-5>, "note": "<one sentence justification>"}

QUERY: {query}

ANSWER: {answer}
```

**How it's actually sent** — `{query}` and `{answer}` get filled in per row (your real query text and the assistant's actual answer text), and it's sent as a single user message to `claude-sonnet-5` with:
- `max_tokens=300`
- `thinking={"type": "disabled"}` (the fix from last message)

**Same rubric text is reused for the local-judge path** (`judge_answer_quality_local`) — only the model and transport differ (Ollama `/api/generate` instead of the Anthropic API), so scores from either path are directly comparable if you ever run the agreement check.

If you want to tune the rubric itself (add a dimension, reword one, change the 1-5 scale), it's the `_QUALITY_RUBRIC` string in `src/quality.py` — one place, used everywhere quality gets scored, so an edit there applies consistently to the pipeline flag, the backfill script, and the local judge together.

What's in here

src/quality.py — extended (not replaced) with the LLM-judge scoring logic, kept separate from the existing ground-truth Banking77/FinQA functions since they're genuinely different mechanisms.

src/pipeline.py — new --score-quality flag. When you run python -m src.pipeline 50 --score-quality, it scores every single row's answer right after all Tier 1/Tier 2 processing finishes (exactly where you asked — after everything else is done), and the quality columns flow automatically into all four output files, since they're added to the row data before any of the four gets written.

scripts/backfill_quality_scores.py — retroactively scores your existing historical rows in results_history.csv, and propagates to results_log_combined.csv + the per-unit file for whichever run is still "current" in them.

What I tested (all against stubbed judges, since I can't call the real API here)
All 4 files get the columns consistently in one pipeline run
Default is OFF — confirmed zero extra API calls unless you pass the flag, so routine runs aren't silently more expensive
A failed judge call doesn't crash the run — that row gets None, everything else proceeds
Backfill is fully idempotent — re-running it made zero API calls and touched zero already-scored rows, so you can run it repeatedly without worrying about double-billing
--unit filtering works correctly
A safety check I added after thinking it through more carefully: the original merge approach joined on query text, which could silently duplicate rows if two sampled queries happened to be identical. I replaced it with positional alignment within each run_id, with a row-count check that skips (and warns) rather than risk writing scores onto the wrong rows if anything's ever out of sync.
Cost/time, worth deciding deliberately

Scoring is one extra Claude call per row. For your n=1000 runs, that's 1,000 extra API calls — real time and real money, which is exactly why this is opt-in rather than always-on. Sensible uses: --score-quality on specific before/after comparison runs, or the backfill script with --limit 100 to start cheap and expand later — not blanket-enabled on every routine test run.

To run once you're ready:

python scripts/backfill_quality_scores.py

then check the new quality_overall column in results_history.csv directly, or point your existing significance-testing instinct at it — it's just a normal column now, so any pandas groupby/t-test works on it without needing a separate script.
